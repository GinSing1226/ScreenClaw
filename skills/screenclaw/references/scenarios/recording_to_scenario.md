# 从录制产物沉淀场景

当用户指定 `record/record_{datetime}` 目录并要求沉淀模板时，使用本流程。目标是理解用户演示过的一次操作，把它抽象为可复用场景模板；不是把录制步骤原样回放。

## 输入文件

录制目录通常包含：

```text
record/record_YYYYMMDD_HHmmss/
├── step.json
├── step_0001.png
├── step_0002.png
├── step_0002_start.png
└── ...
```

`step.json` 提供动作、窗口、进程、百分比坐标、截图文件名和 `window_info`。截图提供操作对象和界面状态。动作截图通常表示本步操作发生时的界面；下一步截图常用于判断上一步操作后的结果。

`window_info` 格式：

```json
{"source_width": 1936, "source_height": 1048, "scale_factor": 1.0}
```

它描述该步骤坐标来源的窗口或桌面坐标空间。固定坐标必须和对应 `window_info` 一起沉淀。

录制不会完整保存鼠标轨迹。hover、无按键鼠标移动、轻微移入菜单等通常不会形成独立步骤，因此相邻截图可能看起来不连贯。分析时要把“记录动作”和“状态形成路径”分开。

## 先补齐最少上下文

不要每一步都问用户。先读取完整 `step.json` 和截图，尽量自动归纳。如果仍缺少关键上下文，只集中问 1-3 个问题：

- 这段录制要沉淀成什么场景。
- 哪些内容未来由用户需求决定，例如账号、联系人、文件名、路径、标题、正文、筛选条件。
- 成功标准是什么，或录制里是否包含误操作、试错、临时输入。
- 如果录制里有中文、IME 或输入法文本，确认最终想输入的语义内容；不要默认录制到的拼音或英文字符就是业务文本。

如果用户已经说明目标，就不要再问这些问题，直接分析。

## 分析步骤

1. **读取元数据**
   - 读取 `step.json`。
   - 先运行窗口组脚本：

     ```bash
     python scripts/recording_windows.py path=record/record_YYYYMMDD_HHmmss
     ```

     将输出的窗口组预处理表作为后续窗口清单、节点层级、固定坐标表和指令变量的事实来源。
   - 统计应用、窗口标题、动作类型、桌面级步骤和缺失截图的步骤。
   - 统计每个坐标空间的 `window_info.source_width/source_height/scale_factor`。同一窗口组内如果 `window_info` 不一致，记录差异并在模板中要求执行时重新截图校验。
   - 不要手工改写窗口组脚本给出的机械类型。可以把 `group_key` 改得更语义化，但类型、步骤归属、主/子窗口关系必须保持一致。
   - 找出明显的阶段切换，例如主应用窗口、系统弹窗、文件选择框、新页面、发布确认页。

2. **按步骤看图**
   - 对每个有截图的步骤，查看本步截图中的标记点位置。
   - 对 drag/swipe，同看 start/end 两张截图。
   - 对没有截图的步骤，使用前后步骤截图和 action/params 推理。
   - 如果本步截图已经出现菜单、浮层、hover 态、展开面板，检查前一步截图是否已经有该状态；如果没有，说明可能存在未录制的 hover/鼠标移入/展开动作。

3. **推理每步目的**
   - 本步动作说明“用户做了什么”。
   - 本步截图说明“用户对哪个对象操作”。
   - 下一步截图说明“这个动作造成什么结果”。
   - 结合三者给步骤归类：导航、选择、输入、确认、等待、试错、清理、提交、验证。
   - `step.json.action` 优先于截图观感，但截图状态可提示缺失前置路径。截图里出现下拉菜单、hover 态、焦点态时，不要把记录的 `click` 改写成 `hover`；应判断复现这个 `click` 前是否需要先 `hover`、`mouse_move` 或点击展开菜单。
   - 判断是否需要补前置 hover/展开动作：
     - 前一步截图没有目标菜单，本步截图已有菜单，且本步点击落在菜单项上。
     - 菜单由带箭头、悬停高亮、贴合父按钮的浮层组成。
     - 同一个 UI 同时支持 hover 和 click 展开时，优先写成“截图确认菜单是否已展开；未展开则 hover 或点击父按钮展开”。

4. **合并为业务节点**
   - 连续完成同一目的的步骤合并成一个节点。
   - 连续退格、误输入、重复点击、拖动标签页等低价值动作，只有对复现有意义时保留。
   - 每个节点写清 T/I/P/O/E，而不是逐条复述录制步骤。
   - 每个节点标明操作层级：主窗口、子窗口、系统弹窗/文件选择框、桌面级。

5. **判定固定或动态**
   - 固定节点：窗口和控件稳定、窗口比例基本一致、坐标不依赖用户本次需求。
   - 动态节点：目标由用户需求决定，或目标在列表/搜索结果/文件系统/页面内容中变化。
   - 动态节点必须写截图定位提示：关注区域、文字/图标/颜色/布局特征、确认标准。

6. **生成指令**
   - 固定节点写成 batch 指令。
   - 动态节点写“先截图定位，读取坐标后执行”的说明，指令中用 `{从截图读取}` 或 `{用户输入}` 占位。
   - 高风险动作必须要求 marker 反验或执行后截图验证。
   - 坐标按录制或截图读数保留小数，不要改成整数。
   - 不要把录制中的中文输入法中间态、拼音或误识别英文固化到模板；改为 `{用户输入}`、`{搜索关键词}`、`{目标文件名}`、`{完整路径}` 等变量。
   - 对疑似未录制 hover/鼠标移入的节点，模板中不要只写“点击菜单项坐标”。应先写状态准备：截图确认菜单/浮层已展开；若未展开，先 `hover`、`mouse_move` 或点击父按钮展开，再点击目标项。
   - 固定坐标节点必须引用窗口清单中的来源 `window_info`，执行时先用 `coord_adapt` 计算候选坐标和复用决策。

## 窗口和进程归纳

录制中的 `process` 是线索，不是模板可直接复用的定位方式。

- 不复用历史 `window_id` 或 `main_window_id`；模板中用明确变量占位，例如 `{publish_content_child_window_id}`、`{publish_main_window_id}`。
- 优先记录稳定锚点：`process_name`、`window_title` 关键词、主窗口标题、子窗口标题、截图内容特征。
- 机械判断窗口类型：
  - `window_id == main_window_id`：主窗口操作。
  - `window_id != main_window_id`：子窗口操作，模板必须在窗口清单、节点操作层级、固定坐标表和指令变量中写明子窗口。
  - `process == null` 或 action 以 `desktop_` 开头：桌面级操作。
  - 标题为 `打开`、`另存为`、`选择文件` 等系统对话框时，通常归纳为系统弹窗；仍按 `window_id/main_window_id` 判断它是弹窗主窗口还是弹窗子窗口。
- 业务命名不能覆盖机械类型。即使窗口代表“小红书页面内容”，只要 `window_title="Chrome Legacy Window"` 且 `window_id != main_window_id`，类型也必须写“子窗口”，不能写“小红书主窗口”。
- Chrome/WebView 常见模式：`main_window_title="xxx - Google Chrome"` 是主窗口锚点，`window_title="Chrome Legacy Window"` 常是实际内容子窗口。若录制坐标落在 `Chrome Legacy Window`，固定坐标必须使用子窗口 ID；主窗口只用于定位、激活和整体验证。
- 生成窗口清单时，同一个业务应用通常需要两行：
  - `{应用}主窗口`：类型 `主窗口`，用于 `get_window_list`、激活、最终截图验证；没有录制固定坐标落在它上面时，不把 `click/input_text` 写成它的可用操作。
  - `{应用}内容子窗口`：类型 `子窗口`，获取方式 `include_children=true` 后按子窗口标题/截图确认；实际固定坐标操作写在这一行。
- 文件选择框、系统弹窗、浏览器唤起的对话框，进程名可能是调用方进程或缺失。此时标题通常更可靠，例如 `打开`、`另存为`、`选择文件`。
- 如果某步骤没有进程名，或进程名明显不是用户要操作的业务窗口，模板应要求：
  1. 调用 `get_window_list include_children=true`。
  2. 用窗口标题关键词筛选候选窗口。
  3. 对候选窗口截图确认内容。
  4. 再填入运行时 `window_id/main_window_id`。

### 窗口组预处理表

从录制沉淀前，先用 `scripts/recording_windows.py|ps1|sh` 生成窗口组。后续模板的窗口清单、节点层级和指令变量必须与此表一致。

| group_key | 类型 | process_name | window_title | main_window_title | 录制步骤 | window_info | 变量名建议 |
|-----------|------|--------------|--------------|-------------------|----------|-------------|------------|
| desktop_monitor_0 | 桌面级 | null | null | null | 1 | source_width=3840, source_height=2160, scale_factor=1.5 | `{desktop_monitor_index}` |
| publish_content_child | 子窗口 | chrome.exe | Chrome Legacy Window | 小红书创作服务平台 - Google Chrome | 2,3,4 | source_width=3840, source_height=1958, scale_factor=1.5 | `{publish_content_child_window_id}`, `{publish_main_window_id}` |
| file_dialog | 系统弹窗主窗口 | chrome.exe | 打开 | 打开 | 5-11 | source_width=1800, source_height=1080, scale_factor=1.5 | `{file_dialog_window_id}`, `{file_dialog_main_window_id}` |

如果某个固定坐标所在步骤属于子窗口，后续固定坐标表的“使用窗口”必须写这个子窗口组名；不能写主窗口组名。

## 跨进程和跨窗口节点

录制中常见的跨进程节点包括：点击上传按钮后打开文件选择框、点击外部应用唤起浏览器、从桌面或资源管理器拖拽到网页、系统确认弹窗出现。

- 跨进程节点的验证截图必须放在跨进程动作之后。
- 执行动作前只能验证“即将点击的对象是否正确”，不能验证动作结果。
- 动作执行后，先重新 `get_window_list include_children=true`，按新窗口标题、进程名和截图内容定位目标。
- 文件选择框等系统弹窗优先使用标题关键词，例如 `打开`、`另存为`、`选择文件`。
- 新窗口定位完成后，再对新 `window_id/main_window_id` 截图确认；不要继续对旧窗口截图。
- 如果跨进程动作本身是桌面级操作，执行后仍应重新选择目标层级：新窗口可用则转窗口级，仍是桌面 UI 才继续桌面级。

## 桌面级步骤归纳

桌面级步骤用于桌面图标、任务栏、系统托盘、开始菜单、跨窗口拖拽、文件选择等场景。

- `monitor_index` 只代表录制时的显示器，不能直接固化为永远正确。
- 模板中的桌面级节点必须先调用 `desktop_get_monitors_list`。
- 单显示器时通常使用 `monitor_index=0`。
- 多显示器时，根据目标窗口、任务栏、桌面元素或用户说明选择显示器，再 `desktop_screenshot`。
- 如果目标可以通过窗口级方式定位，优先转为窗口级操作；只有窗口级不可用或本质是桌面 UI 时保留桌面级操作。

## 坐标复用与候选迁移

模板中的固定坐标是百分比坐标，但它依赖沉淀时的窗口或桌面坐标空间。执行模板时不要手工换算坐标，使用 `scripts/coord_adapt.py|ps1|sh`。

调用示例：

```bash
python scripts/coord_adapt.py \
  source.width={source_width} source.height={source_height} source.scale_factor={source_scale_factor} \
  current.width={current_width} current.height={current_height} current.scale_factor={current_scale_factor} \
  point.x={template_x} point.y={template_y} risk=normal
```

使用规则：

- `direct`：使用返回的 `candidate.x/y` 作为当前坐标，可进入 batch。
- `verify`：用返回的 `candidate.x/y` 打 marker 反验；落在目标对象上才执行。
- `relocate`：不复用固定坐标，按动态定位提示重新读图。

按窗口组懒加载计算：

- 每个窗口组第一次遇到固定坐标时，先截图获取当前 `window_info`，再调用 `coord_adapt`。
- 窗口组示例：发布页子窗口、文件选择框、桌面显示器、系统确认弹窗。
- 同一窗口组缓存一次决策；窗口尺寸、缩放率、`window_id/main_window_id`、`monitor_index` 或页面布局变化后重新计算。
- 如果首个坐标是 `direct`，同组低风险固定坐标可直接使用候选坐标。
- 如果首个坐标是 `verify` 且 marker 通过，同组低风险固定坐标可继续用候选坐标；高风险动作仍需 marker。
- 如果首个坐标是 `relocate` 或 marker 失败，同组固定坐标都不要直接复用。

## 固化与动态判定细则

可固化：

- 稳定导航按钮、固定工具栏按钮、固定弹窗确认按钮。
- 系统文件选择框中的固定输入框、打开按钮等通用控件。
- 与用户目标无关、且窗口比例变化不影响位置的步骤。

应动态：

- 选择特定文件、联系人、会话、账号、商品、列表项。
- 搜索结果、推荐流、瀑布流、分页表格中的目标。
- 根据用户输入内容变化的标题、正文、路径、筛选条件、文件名、搜索关键词。
- 页面加载后位置不稳定的按钮或弹窗。
- 录制中由中文输入法产生的文本，除非用户明确确认，否则都视为动态语义输入。

可删除或合并：

- 误输入后删除。
- 为了暴露 UI 状态产生的临时点击。
- 只改变窗口位置、标签页位置、焦点，但和业务目标无关的动作。
- 重复按键或点击，除非是目标软件必须如此。

## 输出到场景模板

沉淀时按 `template.md` 输出。模板中可以在“场景业务流概述”里简要写明来源，例如：

```text
来源：根据用户录制 record/record_YYYYMMDD_HHmmss 归纳。
```

不要在最终模板中写冗长的逐步内部推理。最终模板只保留可执行的业务节点、固定/动态定位规则、指令和异常处理。

模板的输出状态不能超过录制证据。如果最后一张截图只证明“回到某页面”，但没有证明“上传完成/发送成功/发布成功”，O（输出）必须写成“需继续截图确认某标志出现”，不能直接声明业务已成功。

## 质量检查

生成或更新模板前检查：

- 是否已经从录制步骤抽象为业务节点，而不是逐步复制。
- 是否删除或合并了明显试错步骤。
- 是否把动态输入替换为 `{用户输入}` 或截图定位提示。
- 是否没有复用历史窗口 ID。
- 每个固定坐标是否能追溯到窗口清单中的 `window_info.source_width/source_height/scale_factor`。
- 是否已经先生成窗口组预处理表，并让窗口清单、节点层级、固定坐标表、指令变量与该表一致。
- 如果录制中存在 `window_id != main_window_id`，是否已在窗口清单、节点层级、固定坐标表和指令变量中明确写成子窗口。
- 是否避免把 `Chrome Legacy Window` 这类内容子窗口写成“主窗口”；主窗口只在确实 `window_id == main_window_id` 或用于定位/验证时写主窗口。
- 是否按 `step.json.action` 归纳动作，没有把 click 后出现的菜单误写成 hover。
- 如果截图状态依赖未录制的 hover/鼠标移入/展开动作，是否在模板中补了状态准备步骤。
- 中文或 IME 文本是否已语义化为变量，而不是固化录制到的拼音/英文中间态。
- 文件选择框或系统弹窗是否使用标题关键词定位。
- 桌面级操作是否包含显示器枚举和运行时选择。
- 高风险动作是否有 marker 反验或截图验证。
- 输出和完成状态是否有截图证据支撑。
- 模板是否说明执行时使用 `coord_adapt`，而不是让 AI 手工换算坐标。
