# 文档管理规范

> 索引：[需求文档目录](../0.需求文档目录.md)

本文规范需求文档的结构、索引机制、元数据规范，确保AI协作和项目管理的可维护性。

---

## 文档结构方案

### 文档长度规范

| 文档长度 | 规范 |
|----------|------|
| **< 300行** | 单文档，推荐结构 |
| **300-500行** | 单文档 + 明确的章节锚点 |
| **> 500行** | 考虑按职责拆分（如「需求文档」「API文档」「实现指南」） |


### AI读取机制

AI读取文档**不是一次性读取整个文档**，而是：

1. **Read工具支持分段**：可以通过 `offset` 和 `limit` 参数分部分读取
2. **Grep工具搜索定位**：先用Grep搜索关键词定位到相关章节，再用Read读取
3. **按需读取**：根据任务类型决定读取深度
   - 理解需求：读取"需求描述"部分
   - 编码实现：读取"技术描述"部分
   - 代码review：可能都需要读

## 元数据规范

### YAML元数据块

每个文档开头必须包含YAML元数据：

```yaml
---
name: 功能名称
description: 功能简述（1-2句话）
---
```
### 元数据字段说明

| 字段 | 说明 | 示例 |
|------|------|------|
| **name** | 功能名称（与文档标题一致） | `助手CRUD` |
| **description** | 功能简述（关键词、可搜索） | `助手的新增、编辑、删除功能` |

### 状态标记

在文档开头的状态栏中使用统一标记：

| 标记 | 含义 |
|------|------|
| ✅ | 已实现 |
| 🚧 | 开发中 |
| ⏸ | 待开发 |
| 🔜 | 后续迭代 |

### 优先级标记

| 优先级 | 说明 |
|--------|------|
| P0 | 核心功能，必须实现 |
| P1 | 重要功能，优先实现 |
| P2 | 次要功能，可延后 |

## 索引机制

### 索引原则

1. **渐进式披露**：不要一个目录索引所有文件，建议一个目录索引同级及下级共2层
2. **双链索引**：如果文档A被文档B索引了，文档A需要有文档B的索引条目，文档B也要有文档A的索引条目
3. **同步更新**：修改文件名后，需要同步修改相关索引的相对路径

### 索引条目格式

```
元数据-名称：元数据-描述。[名称](文件相对路径)
```
### 功能清单索引示例

```markdown
## 功能模块

| 功能 | 状态 | 文档 |
|------|------|------|
| 功能名称 | ✅ | [功能文档](./功能文档.md) |
```
### 相关文档索引

每个文档末尾必须有"相关文档"章节：

```markdown
## 相关文档

- 关联：[相关功能1](./相关功能1.md) | [相关功能2](./相关功能2.md)
- 上层：[上层文档](../上层文档.md)
- 原文档：[原始文档](../原始文档.md)
```
---

## 修改规范

1. **先更新文档，后修改代码**：确保文档和代码保持同步
2. **同步更新索引**：修改文档名或路径后，同步更新所有相关索引
3. **保持版本一致**：文档中的状态标记需与实际开发进度一致
4. **双链检查**：添加新文档时，检查并更新所有相关文档的双链索引

## AI协作提示

### 给AI的提示

当AI需要读取需求文档时，可参考以下策略：

1. **先读元数据和目录**：快速了解文档结构
2. **按需读取章节**：根据任务类型选择读取"需求描述"或"技术描述"
3. **使用Grep定位**：搜索关键词（如接口名、组件名）快速定位
4. **分段读取长文档**：使用offset/limit参数分部分读取

### 给用户的提示

1. **保持文档简洁**：避免过度冗长的描述，专注核心信息
2. **使用标准格式**：遵循本文档规范的结构模板
3. **及时更新状态**：功能开发进度变化时，同步更新状态标记
4. **定期检查索引**：确保索引链接有效，双链索引完整
